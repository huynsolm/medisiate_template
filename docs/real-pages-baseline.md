작성: 2026-11-16. 사용자가 `reference/cms-original/`(main `591cff6`)에 원본 자료를 올렸다.

| 폴더 | 내용 |
|---|---|
| `component/` | 원본 CMS 도구의 타입 컴포넌트 HTML 37개(type00~type36). 옵션 설명 주석 포함 |
| `css/` | 원본 `cms.css`, `cms-blue.css`, `cms-nanum.css` |

## 1. 왜 다시 맞추는가

3·4단계 타입은 biny cms-preview 재현본(`fixtures/original`)을 원본 구조 기준으로 만들었다. 진짜 원본 컴포넌트와 실제 페이지로 돌려 보니 **재현본과 구조가 다른 곳**이 있었다.

- type10: 육각형 안 핵심 단어가 진짜 원본은 `p.cms-description`(재현본은 `p.cms-title`) → 실제 130개 섹션 **전부** fallback이었다.
- type26: 진짜 원본은 표에 `caption.sr-only`(표 제목)가 있다 → 실제 106개 중 103개 fallback이었다.
- 여러 타입: 실제 페이지는 `li > div.row > .cms-visual`처럼 항목 안에 감싸는 상자를 넣는다 → 직접 자식만 보던 파서가 이미지·글을 못 찾았다.
- type26: 실제 페이지에 `width:*`, `width:%` 같은 오타와 `width="20%"` 속성 표기가 있다 → 오타를 그대로 담아 스키마가 섹션을 거부(`INVALID_DATA`)했고, 속성 표기 너비는 잃고 있었다.

## 6. 링크 (모든 타입 공통, 경고 없는 손실이었음)

실제 페이지에 `<a href>` 링크가 367개 있다(주석 안 제외 시 섹션 안 링크 기준). 서식 허용 목록에 `a`가 없어 **글만 남고 주소가 사라졌는데 success**였다(경고 없음). 제안서도 "링크는 텍스트·밑줄·명시적 버튼 형태로 정적 표현"이라 링크는 남아야 한다.

- 글 안 링크: `a`를 서식 허용 목록에 넣고 주소를 검사한다(`safeHref`, `packages/core/src/html/rich-text.ts`). http(s)·mailto·tel·상대 주소(`/a`, `../a`, `a.html`, `#id`)만 허용. 브라우저처럼 탭·줄바꿈을 지운 뒤 scheme을 본다(`java\tscript:` 차단). `target="_blank"`는 `rel="noopener noreferrer"`와 함께 유지. 다른 속성(onclick, data-toggle 등)은 버린다.
- 위험한 주소는 글만 남기고 **`UNSAFE_LINK_REMOVED` 경고**를 남긴다(실제 페이지에는 0건).
- 이미지를 감싼 링크(동영상 썸네일 `<a href><img></a>`): 이미지 참조에 `link`·`newTab`을 두고 같은 주소 검사를 거쳐 다시 감싸 출력한다. 편집기·JSON으로 들어온 링크도 스키마에서 검사한다.
- 확인: 페이지마다 "원본 섹션 안 링크 수(주석 제외)"와 "출력 링크 수(fallback 원본 보존분 포함)"를 비교해 **줄어든 페이지 0개**.

### type33 Q&A (섹션별 모드)
type33의 Q&A 아코디언은 호스트 `mig-faq-*`가 맞는데, 이 규칙은 **일반 모드에만** 있다. 그래서 타입 정의에 섹션별 모드 선택(`strategyFor`)을 더했다.
- 원 목록 형태 → 프리셋(type-27 카드), Q&A 형태(원본 `dl.cms-inner-box` 또는 편집기에서 Q&A 항목을 넣은 경우) → 일반 모드. 한 페이지에 섞이면 변환기가 블록을 나눠 각자 `.migration-content`로 감싼다(호스트 FAQ 규칙은 `.mig-container`가 없는 감싸개에서만 적용).
- 출력: `.mig-faq-wrap > .mig-faq-item > .mig-faq-question(strong.mig-title) + .mig-faq-answer(p.mig-desc[, ul])`. 원본은 질문을 눌러 펼치지만 제안서 원칙대로 답을 모두 펼친다. 원본의 Q·A 표시 span은 호스트 CSS(::before)가 다시 그리므로 옮기지 않는다.
- 글 순서 검사는 타입이 선언한 표시 요소만 뺀다(`orderCheckIgnores`, type33은 dt·.copy 바로 아래의 Q/A 한 글자 span). 다른 곳의 "Q" 글자는 그대로 검사한다.
- 답 = 목록 앞 글 + 첫 목록(`ul.cms-list-box`). 목록 뒤 글이나 두 번째 목록은 담지 않아 fallback.
- 질문의 아코디언 `button`은 줄 안 요소로 인정(글 유지, 펼치기 동작은 정적 표현).
- Chromium(호스트 CSS) 확인: Q·A 표시가 그려지고 답이 모두 보인다. 실제 Q&A 섹션 4개 변환(질문 button 허용 후), type33 63% → 70%.

## 9. 원본 보존 섹션 줄이기 (구조 일치 재분류 + 블록 순서 변환)

작성: 2026-11-17. 사용자 결정: 두 방식을 함께 쓴다.

### 9.1 출발점
원본 보존(fallback) 섹션 428개를 사유별로 나누면 대부분 "적힌 타입 구조에 블록이 하나 더 붙은" 경우였다(type01에 이미지 묶음이 두 번, type02로 적혔지만 type17의 행 목록, 머리글·이미지·설명 상자·표·버튼이 섞인 구성). 원본 `cms.css`는 타입 번호가 아니라 목록·상자 클래스(`.cms .cms-row-list` 등)로 모양을 정한다.

### 9.2 순서 (`convert-document.ts`)
1. 적힌 타입으로 옮긴다(지금과 같음).
2. 실패하면 **구조 일치 재분류**: 섹션 안의 `cms-*` 클래스가 모두 어떤 타입의 원본 컴포넌트(`reference/cms-original/component/typeNN.html`)에 있는 클래스이고, 그 타입을 가르는 구조 클래스(공통 클래스 header·title·description·visual·list-item 등 밖의 것)를 하나 이상 쓰면 그 타입으로 옮겨 본다. 클래스 표는 `packages/core/src/types/structure-classes.ts`(자동 생성, 테스트가 원본과 같은지 검사). 성공하면 `STRUCTURE_RETYPED`(info).
3. 그래도 실패하면 **블록 순서 변환**(`types/blocks.ts`, 일반 모드 `mig-section type-text`): 머리글(작은 글·제목)·제목·글·이미지(PC/MO 쌍)·목록(3단계까지, 번호 시작값)·표(병합·열 너비)를 원본 순서대로 늘어놓는다. 배치(열 수·카드·장식)는 호스트 기본 모양이 되므로 `LAYOUT_SIMPLIFIED`(warn) → 파일은 확인 대상(partial). 지원하지 않는 타입이면 `UNSUPPORTED_TYPE`도 함께 남겨 unsupported 목록에 계속 나온다.
4. 그래도 실패하면 지금처럼 원본 보존.

모든 단계에 같은 손실 검사(`finish`: 글·이미지·글 구조·중복 읽기)와 화면별 글 순서 검사가 적용된다. 시도마다 읽기 기록(`resetReads`)을 지워 앞선 시도가 다음 시도의 검사에 섞이지 않게 했다(처음에 이 누수로 37개 섹션이 잘못 거부됐다).

블록 순서 변환이 원본을 보존하는 경우: 동영상·지도·입력란(`iframe`·`video`·`form` 등), 글이 든 도형 SVG, 4단계 이상 목록, 표 칸 안의 목록, 한 화면 안에서 폭에 따라 바뀌는 표시, 호스트 CSS가 모르는 표시 클래스로 숨긴 글.

### 9.4 검사
- 타입 parser의 안전 검사(기존 테스트)는 블록 순서 변환을 뺀 레지스트리(`typedRegistry`)로 계속 "담지 못하면 원본 보존"을 확인한다. 블록 순서 변환 자체는 `blocks.test.ts`, 재분류는 `structure-retype.test.ts`, 브라우저 배치는 `tests/visual/blocks-layout.test.ts`(PC 1100 / MO 360: 넘침 없음, PC/MO 이미지 한 장씩, 중첩 목록·표가 섹션 안).
- 실제 페이지 순서 검사(`every converted section keeps the original text in the same order`)는 블록 순서 섹션도 포함해 통과.

### 9.5 한계
- 블록 순서 섹션은 원본 고유 배치(여러 열 카드, 도형, 강조 상자 색 등)를 잃는다. 내용·순서·이미지·링크는 같다.
- 편집기의 블록 필드는 목록 항목 안 블록까지(제목·글·이미지)만 고칠 수 있고, 표 칸은 편집기에서 고치지 않는다(데이터는 그대로 보존).

## 10. 블록 순서 섹션 줄이기 1: 본문 앞뒤 설명 상자 (section.notes)

작성: 2026-11-17. 사용자 결정: 블록 순서 섹션을 원본 배치(프리셋)로 되돌리는 작업을 진행.

### 10.1 원인 분석
블록 순서 섹션 352개마다 "어떤 부분을 빼면 적힌 타입이 옮겨지는지"를 실험했다(scratchpad 분석 스크립트).

| 빼 본 부분 | 섹션 수 |
|---|---:|
| 타입 구조 밖 설명 상자(.cms-inner 바로 아래 .cms-description-box) | 70 |
| 항목 안 목록 | 19 |
| 둘째 이미지 묶음 | 12 |
| 버튼 영역 | 6 |
| 둘째 머리글 | 5 |
| 한 가지를 빼서는 안 됨(여러 원인·고유 구조) | 220 |

### 10.2 수정
- **섹션 공통 본문 앞뒤 설명**(`SectionModel.notes = { intro?, note? }`, 스키마 `sectionSchema.notes`): 타입 구조 밖 설명 상자를 담는다. 프리셋 골격(`presetSection`)이 출력한다.
  - 본문 앞(intro) → 머리글 설명 자리 `.mig-header > p.mig-desc`. 본문 맨 앞에 두면 호스트의 `.mig-body > .mig-list:first-child` 같은 규칙이 깨진다.
  - 본문 뒤(note) → `.mig-body` 끝의 `.mig-text-wrap > p.mig-desc`.
- **변환 순서**(`convert-document.ts` `attemptWithNotes`): 적힌 타입 실패 → 설명 상자를 떼고 같은 타입으로 다시 → 구조 일치 재분류 → 블록 순서 → 원본 보존.
  - 상자가 본문 사이에 끼어 있거나, 글로 옮길 수 없는 구조(목록·표·이미지)가 들어 있으면 시도하지 않는다.
  - 상자를 뗀 나머지는 타입의 손실 검사, 설명을 붙인 결과 전체는 원본 전체와 화면별 글 순서 검사를 받는다. 프리셋 골격을 쓰지 않는 타입은 설명이 출력되지 않아 순서 검사에서 걸러진다(블록 순서로 감).
  - 원본 DOM은 잠시 상자를 뗐다가 그대로 되돌린다(같은 입력을 다시 변환해도 결과가 같음을 테스트).
- **편집기**: 프리셋 섹션에 "본문 앞뒤 설명 (섹션 공통)" 칸을 추가했다. 둘 다 비우면 필드를 지운다.
